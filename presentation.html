Проблема не в промптингу.

Проблема — у передачі контексту.

Ідея в моїй голові → AI-агент. Як передати? Три симптоми того, що контекст не долетів:

  • Галюцинації (API, яких не існує)
  • Втрата контексту в довгих сесіях
  • Inconsistency між запусками

Чому це особливо боляче для JS-розробника

  • JavaScript ecosystem = постійна зміна API (Next.js App Router, Bun/Deno, нові TS features, framework churn)
  • AI без контексту пише код під застарілі версії.

Counter-measure: Context7 MCP

"mcpServers": {
  "context7": {
    "url": "https://mcp.context7.com/mcp",
    "headers": {}
  }
}

Context7 = контекст для бібліотек. Решта доповіді = контекст для твого проекту.

Якість коду на виході
= якість специфікації на вході.

Посилюємо Plan Mode через custom skills

Plan Mode сам не витягує контекст — він припускає. Рішення: skill, що примушує агента інтерв'ювати тебе.

grill-me by Matt Pocock

github.com/mattpocock/skills/grill-me · YouTube demo 

---
name: grill-me
description: Interview the user relentlessly about a plan or design
  until reaching shared understanding, resolving each branch of the
  decision tree. Use when user wants to stress-test a plan, get
  grilled on their design, or mentions "grill me".
---

Interview me relentlessly about every aspect of this plan until we
reach a shared understanding. Walk down each branch of the design
tree, resolving dependencies between decisions one-by-one. For each
question, provide your recommended answer.

Ask the questions one at a time.

If a question can be answered by exploring the codebase, explore
the codebase instead.

Plan Mode: де все одно ламається

  • Довгі сесії — контекст розмивається з кожним turn
  • Міжфайлові зміни — агент забуває, що робив 10 хв тому
  • Немає persistence — план помирає разом із сесією

Етап 2

Потрібна "пам'ять" — знайомтесь, ADR

Architecture Decision Records

  • Короткий markdown: context → decision → consequences
  • Живе в кодовій базі: docs/adr/
  • Приклад з yoga-dashboard: ADR-003: Why we chose Server Actions over API routes

Ідея 2011 року (Michael Nygard). Друга молодість — тепер читають не лише люди, а й агенти.

Як навчити агента створювати ADR

Додаєш CLAUDE.md / .cursorrules з інструкцією:

## Architecture decisions

When you make a non-trivial architectural choice,
create or update an ADR in docs/adr/.
Format: context → decision → consequences.
Link to the ADR from any PR it affects.
  • Агент сам заповнює ADR під час роботи
  • Наступна сесія → агент читає docs/adr/ → розуміє історію рішень

ADR: плюси і мінуси

✓ Плюси

  • Легко впровадити, низький поріг входу
  • Люди теж читають — команда виграє

✗ Мінуси

  • Non-standard формат — кожна команда винаходить свій
  • Агент не завжди знає, коли створювати ADR
  • Залишається відкрите: що з feature-level специфікаціями?
Етап 2.5

GitHub Spec Kit — спробували, не зайшло

"А що як формалізувати все?"

  • Структурована ієрархія: project → epic → feature → task
  • Ідея приваблива, реальність — too heavy для нашої команди
  • На довгій дистанції важко підтримувати — документи розбігаються з кодом
Good idea, wrong weight class. Для enterprise з compliance — працює. Для команди ≤ 5 — overhead > value.
Етап 3

OpenSpec

A YC-backed startup (W'26) by Fission-AI — lightweight and adaptable.

Core promise: "Agree before you build"

Philosophy: fluid not rigid · iterative not waterfall · built for brownfield not just greenfield

Positioning: vs Spec Kit (heavyweight, Python setup) · vs Kiro (IDE-locked, Claude-only)

Одна change — одна папка

openspec/changes/add-weekly-streak-badge/
  proposal.md    # чому і що змінюється
  specs/         # requirements + scenarios
  design.md      # технічний підхід
  tasks.md       # implementation checklist

Мінімально — 4 файли, кожен з конкретною роллю.

Running example: feature з yoga-dashboard.

Дві двері в OpenSpec

Залежно від того, наскільки ясно ти бачиш задачу.

A · Propose

Ти знаєш, що хочеш.

/opsx:propose \
  "add weekly streak badge"

→ proposal, specs, design, tasks

B · Explore

Ти ще не знаєш, що саме хочеш.

/opsx:explore [topic]

→ розмова, діаграми, без artifacts. Переходить у propose, коли ясність прийде.

Docs: commands.md#opsxexplore

Lifecycle: specs as throwaway artifacts

/opsx:propose spec IN
→
/opsx:apply code OUT
→
/opsx:archive forget
↓
openspec/changes/archive/
2026-05-23-streak-badge/
Ти НЕ підтримуєш документацію.
Archive — і рухаєшся далі.

OpenSpec — це фреймворк, не монолит

Дефолтів достатньо на 80% задач. Решта — розширюється.

Custom skills

  • Brownfield-аналіз (initial specs з existing TS)
  • Testing-first flow
  • Команд-специфічні: a11y-check, code review

Agent personas

  • Frontend specialist (React/Next, Tailwind, a11y)
  • API / backend agent (Server Actions, DB, types)
  • Reviewer agent (читає PR проти acceptance)

Один OpenSpec → кілька агентів з різними personas → результат когерентний.
